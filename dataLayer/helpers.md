# Клиентские приёмы

Документ показывает, как клиент получает значения, которые требуют [Общие правила передачи в
dataLayer](dataLayer.md), и как устанавливает факт показа элемента. Норм он не вводит: что
именно передавать, задают общий документ и документ блока.

| --- | --- |

| Значение `event_id` | [3](#3-идентификатор-события) |

| Момент вызова `dataLayer.push` | [5](#5-планирование-push) |

1. Приёмы одинаковы для всех блоков сайта: документ блока их не переопределяет.
2. Код приведён на ES5 без зависимостей: он выполняется до и вне фреймворка приложения.
3. Функция `newId()` [раздела 3](#3-идентификатор-события) дословно совпадает с [Правилами
   передачи в dataLayer 6](../taxonomy/datalayer.md#6-идентификаторы): это одна функция в двух
   документах, и расходиться копии не должны.

## 2. Время события

```js
var occurredAt = new Date().toISOString();
```

1. Значение фиксируется в момент факта, а не в момент push.
2. Формат — UTC с миллисекундами; смещение часового пояса не передаётся.
3. `Date.now()`, локальное время и время сервера в `occurred_at` не передаются.
4. При повторной передаче того же факта `occurred_at` сохраняется.

## 3. Идентификатор события

| Свойство | Формат | Когда генерируется | Сколько живёт |
| --- | --- | --- | --- |
| `event_id` | UUID v4 | В момент факта события | Одно событие |

UUID v4 по RFC 4122: 36 символов, нижний регистр, дефисы на позициях 9, 14, 19, 24.

Функция `newId` должна быть объявлена внутри документа HTML до подключения GTM и быть доступной в скопе window.

Источник случайности выбирается по первой доступной ветке:

| Уровень | Условие | Источник случайности |
| --- | --- | --- |
| 1 | Есть `crypto.randomUUID` | Генератор браузера |
| 2 | Есть `crypto.getRandomValues` | CSPRNG браузера |
| 3 | Нет ни того, ни другого | `Math.random` с примесью времени |

```js
function newId() {
  var c = window.crypto || window.msCrypto;

  if (c && typeof c.randomUUID === 'function') {
    return c.randomUUID();
  }

  var b, i;

  if (c && typeof c.getRandomValues === 'function') {
    b = new Uint8Array(16);
    c.getRandomValues(b);
  } else {
    b = [];
    var time = new Date().getTime();
    for (i = 0; i < 16; i++) {
      var rnd = Math.random() * 256;
      if (time > 0) {
        rnd = (rnd + (time & 0xff)) % 256;
        time = Math.floor(time / 256);
      }
      b[i] = Math.floor(rnd);
    }
  }

  b[6] = (b[6] & 0x0f) | 0x40;
  b[8] = (b[8] & 0x3f) | 0x80;

  var h = [];

  for (i = 0; i < 16; i++) {
    h.push((b[i] + 0x100).toString(16).slice(1));
  }

  return h.slice(0, 4).join('') + '-' + h.slice(4, 6).join('') + '-' +
    h.slice(6, 8).join('') + '-' + h.slice(8, 10).join('') + '-' +
    h.slice(10, 16).join('');
}
```

1. `crypto.randomUUID` существует только в защищённом контексте и не во всех браузерах: ветка
   `getRandomValues` обязательна.
2. `Uint8Array` создаётся только в ветке 2: браузер без `getRandomValues` не имеет и
   `Uint8Array`, поэтому в ветке 3 используется обычный массив.
3. `Math.random` — источник последней очереди: идентификатор из ветки 3 не криптостойкий.
4. Примесь времени в ветке 3 энтропию не добавляет: она разводит значения между загрузками
   страницы на движках с одинаково засеянным `Math.random`.
5. Новый `event_id` на каждый факт; при повторной передаче того же факта `event_id` сохраняется.
6. Идентификатор не выводится из данных пользователя и не строится как время плюс счётчик:
   время в ветке 3 — примесь к случайному байту, а не основа значения.
7. Функция общая: любой будущий идентификатор формата UUID v4 берётся у неё же.

## 4. Отслеживание показа

Факт показа устанавливает браузерное API `new IntersectionObserver(callback, options)`.
Обработчик `scroll` и опрос `getBoundingClientRect()` для этого не годятся: они считают геометрию
в основном потоке на каждый кадр и частоту проверок не ограничивают. Наблюдатель считает
пересечение вне основного потока и зовёт callback только при переходе через порог.

Опции:

| Опция | Значение | Смысл |
| --- | --- | --- |
| `root` | `null` | Область пересечения — окно браузера |
| `threshold` | `[0.8]` | Доля площади элемента, при которой callback вызывается |
| `rootMargin` | не задаётся | Границы области не сдвигаются |

Константы — предложение до согласования [раздела 6](#6-открытые-вопросы):

| Константа | Значение | Смысл |
| --- | --- | --- |
| `VIEW_THRESHOLD` | `0.8` | 80% площади элемента в области видимости |
| `VIEW_DURATION` | `1000` мс | Непрерывная видимость, после которой факт установлен |

```js
var VIEW_THRESHOLD = 0.8;
var VIEW_DURATION = 1000;

function createViewTracker(onView) {
  var timers = new WeakMap();

  var observer = new IntersectionObserver(function (entries) {
    entries.forEach(function (entry) {
      var visible = entry.isIntersecting &&
        entry.intersectionRatio >= VIEW_THRESHOLD;

      if (visible) {
        if (timers.has(entry.target)) return;
        timers.set(entry.target, setTimeout(function () {
          timers.delete(entry.target);
          observer.unobserve(entry.target);
          onView(entry.target);
        }, VIEW_DURATION));
      } else {
        clearTimeout(timers.get(entry.target));
        timers.delete(entry.target);
      }
    });
  }, { root: null, threshold: [VIEW_THRESHOLD] });

  return {
    watch: function (el) { observer.observe(el); },
    stop: function () { observer.disconnect(); }
  };
}
```

Применение — один наблюдатель на показ коллекции:

```js
var tracker = createViewTracker(function (el) {
  var message = viewedMessage(cardDataOf(el));
  schedulePush(function () { pushMessage(message); });
});

cards.forEach(tracker.watch);
```

1. `root: null` достаточно. Отдельный наблюдатель на карусель не нужен: карточка, уехавшая за
   край карусели, обрезана её `overflow` и в пересечение с окном не попадает.
2. Сравнение идёт по `intersectionRatio`, а не по одному `isIntersecting`: последний истинен уже
   при одном видимом пикселе.
3. Таймер даёт непрерывность: уход из области видимости раньше срока снимает таймер, и факта не
   возникает.
4. `unobserve` сразу после факта даёт один факт на элемент за время жизни наблюдателя. Время
   жизни наблюдателя и есть та граница «текущего показа», которой оперирует ключ дедупликации
   документа блока.
5. Возврат к коллекции — новый наблюдатель: `stop()` при уходе с поверхности,
   `createViewTracker()` при следующем показе.
6. При виртуализации списка переиспользованный узел снимается с наблюдения и ставится заново:
   иначе факт припишется тому элементу, который был в этом узле раньше.
7. Rerender наблюдения не сбрасывает и факта не создаёт.
8. `onView` получает узел, но свойства события берутся из данных элемента, а не из DOM: `id`,
   `data-*`, CSS-класс и текст источниками значений не являются — [Общие
   правила 6.6](dataLayer.md#6-свойства-контейнера).
9. Нет `IntersectionObserver` — событий `viewed` нет вовсе. Эмуляция через `scroll` запрещена:
   она даёт другой факт под тем же именем.
10. Наблюдатель — приём установления факта, а не само событие. Push выполняет вызов `onView` —
    [Общие правила 2](dataLayer.md#2-что-передаётся-в-datalayer) и
    [раздел 5](#5-планирование-push).

## 5. Планирование push

Планирование `dataLayer.push` нужно, чтобы передача аналитических событий сохраняла отзывчивость
интерфейса. Для этого клиент ставит готовые сообщения в очередь и передаёт их небольшими
порциями, между которыми браузер получает возможность обновить страницу и обработать действия
пользователя.

Особенно это важно для событий показа. Несколько карточек могут одновременно попасть в область
видимости и почти одновременно выполнить условие длительности из
[раздела 4](#4-отслеживание-показа). За короткое время возникает много событий, каждое из которых
требует двух вызовов `push`: сбрасывающего и событийного —
[Общие правила 4](dataLayer.md#4-структура-сообщения). Например, 27 показов дают 54 сообщения
для обработки тег-менеджером.

Обработка сообщений занимает время основного потока браузера, который также выполняет
JavaScript интерфейса, обрабатывает пользовательский ввод и участвует в отрисовке страницы.
Чем дольше аналитическая работа занимает этот поток без перерыва, тем дольше могут ждать
остальные задачи. При массовых показах это создаёт риск рывков прокрутки и задержек реакции
на нажатия — [Ограничения получателей 5](limits.md#5-основной-поток-клиента).

Очередь ниже распределяет эту работу между ближайшими кадрами. Сообщение собирается сразу при
возникновении факта: его свойства, `occurred_at` и `event_id` уже зафиксированы. Затем очередь
последовательно выполняет пары «сбрасывающий push + событийный push» и после каждой пары
проверяет затраченное время. Когда выделенный бюджет исчерпан, оставшиеся сообщения переходят
в следующую порцию. Состав сообщений и порядок событий сохраняются.

Начало порции планируется через `requestAnimationFrame` и следующий за ним `setTimeout`, чтобы
дать браузеру возможность сначала отрисовать кадр. Запасной таймер позволяет продолжить
обработку, если вызов `requestAnimationFrame` задерживается, например в фоновой вкладке.

При частоте обновления экрана 60 Гц между кадрами проходит около 16,7 мс. Это время требуется
и самому интерфейсу, поэтому для одной порции push предлагается бюджет 4 мс. Он служит условием
остановки между парами push: уже начатая пара выполняется до конца и может превысить бюджет.
Значения ниже предварительные; их нужно проверить на рабочем контейнере и целевых устройствах.

Константы — предложение до согласования [раздела 6](#6-открытые-вопросы):

| Константа | Значение | Смысл |
| --- | --- | --- |
| `PUSH_BUDGET` | `4` мс | Время, дольше которого порция push основной поток не занимает |
| `PAINT_FALLBACK` | `200` мс | Срок, после которого порция уходит без кадра |

```js
var PUSH_BUDGET = 4;
var PAINT_FALLBACK = 200;

function afterPaint(fn) {
  var done = false;

  function run() {
    if (done) return;
    done = true;
    fn();
  }

  if (typeof window.requestAnimationFrame === 'function') {
    window.requestAnimationFrame(function () { setTimeout(run, 0); });
    setTimeout(run, PAINT_FALLBACK);
  } else {
    setTimeout(run, 0);
  }
}

function createPushQueue() {
  var queue = [];
  var scheduled = false;

  function schedule() {
    if (scheduled) return;
    scheduled = true;
    afterPaint(drain);
  }

  function drain() {
    scheduled = false;
    var started = new Date().getTime();

    while (queue.length) {
      queue.shift()();
      if (new Date().getTime() - started >= PUSH_BUDGET) break;
    }

    if (queue.length) schedule();
  }

  return function (fn) {
    queue.push(fn);
    schedule();
  };
}

var schedulePush = createPushQueue();
```

1. Очередь одна на страницу: она разводит по кадрам все события клиента, а не только `viewed`.
2. Сообщение собирается в момент факта, а очередь получает уже готовое. `occurred_at` и
   `event_id` берутся при постановке в очередь, а не при вызове `dataLayer.push`: иначе время
   факта подменится временем отправки — [раздел 2](#2-время-события).
3. Сбрасывающий и событийный push — одна задача очереди, а не две: разрывать пару нельзя, иначе
   сбрасывающий push очистит модель уже после того, как событие ушло.
4. `queue.shift()` сохраняет порядок фактов: очередь их не переставляет и не сливает.
5. Порция ограничена временем, а не числом сообщений: при дешёвом контейнере пачка уйдёт за один
   кадр, при дорогом — растянется на несколько.
6. `setTimeout(run, 0)` внутри `requestAnimationFrame` переносит работу за отрисовку кадра, а не
   в его конец: до отрисовки очередь основной поток не занимает.
7. `PAINT_FALLBACK` нужен фоновой вкладке: `requestAnimationFrame` там не вызывается, и без
   запасного таймера события не ушли бы вовсе. Флаг `done` не даёт выполнить порцию дважды.
8. Планирование не является батчингом, буферизацией и отложенной отправкой — [Общие
   правила 2](dataLayer.md#2-что-передаётся-в-datalayer): сообщения не копятся до порога, не
   сливаются в одно и не ждут события-триггера. Задержка — единицы кадров на порцию.
9. Наблюдатель [раздела 4](#4-отслеживание-показа) очередью не правится: он сообщений не
   отправляет, а `setTimeout` в нём отмеряет непрерывность видимости, а не темп push.
10. Группировку событий выполняет получатель самостоятельно и по своим правилам — [Ограничения
    получателей 2](limits.md#2-группировка-событий). Клиент на неё не влияет и её не эмулирует.

## 6. Открытые вопросы

1. Значения `VIEW_THRESHOLD` и `VIEW_DURATION`: `0.8` и `1000` мс предложены, но не согласованы.
   До согласования события `viewed` в разработку не передаются.
2. Минимальная поддерживаемая версия браузера: от неё зависит, нужна ли ветка 3
   [раздела 3](#3-идентификатор-события) и доступен ли `IntersectionObserver`.
3. Чем ограничен показ коллекции, если поверхность не размонтируется, а перерисовывается на
   месте: время жизни наблюдателя тогда задаётся явным вызовом `stop()`.
4. Значения `PUSH_BUDGET` и `PAINT_FALLBACK` [раздела 5](#5-планирование-push): `4` и `200` мс
   предложены исходя из бюджета кадра, но на боевом контейнере не измерены.
