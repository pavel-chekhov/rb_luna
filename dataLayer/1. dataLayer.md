# Общие правила передачи в dataLayer

Документ задаёт общее для всех блоков сайта: что попадает в dataLayer, как устроено сообщение и
какие свойства несёт любое событие. Событий он не перечисляет — их задаёт документ блока.

## 1. Назначение

Папка `dataLayer/` устроена в два слоя. Этот документ — верхний: он один на весь сайт. Документ
блока — нижний: он описывает события своего блока и общее не переписывает.

| Слой | Документ | Что задаёт |
| --- | --- | --- |
| Общий | `1. dataLayer.md` | Объявление, структуру сообщения, общие свойства, имена событий, приёмку |
| Блок | `2. welcome_pack.md` и следующие | Описание блока, каталоги имён, реестр своих событий; для UI — дерево контейнеров, для Flow — правила попытки |
| Вспомогательный | [helpers.md](helpers.md) | Как клиент получает `occurred_at` и `event_id`, как устанавливает факт показа и как планирует push. Норм не вводит |
| Вспомогательный | [limits.md](limits.md) | Ограничения получателей событий и следствия из них. Норм передачи не вводит |

1. Новый блок сайта добавляется в папку своим документом; этот документ при этом не меняется.
   Единственное исключение — словарь действий [раздела 7](#7-имена-событий): блок, вводящий
   действие, которого в словаре ещё нет, пополняет его строкой, а не объявляет действие у себя.
2. Документ блока ссылается на разделы этого документа и не повторяет их содержимое.
3. Разбиение на блоки следует интерфейсу, а не команде разработки: блок — это связная часть
   сайта со своим деревом контейнеров.
4. Норм таксономии документ не вводит: имена событий, свойств и правила объекта заданы в
   [taxonomy/](../taxonomy/). Здесь — только передача с клиента.

## 2. Что передаётся в dataLayer

Событие описывает факт, который состоялся. Признак факта — его можно назвать в прошедшем
времени и указать момент, в который он случился.

1. Push выполняется в момент факта.
2. Порядок push соответствует порядку фактов.
3. Батчинг, буферизация и отложенная отправка запрещены: сообщения не копятся до порога, не
   сливаются в одно и не ждут события-триггера.
4. Планирование push в ближайшие кадры отложенной отправкой не является — [Клиентские приёмы
   5](helpers.md#5-планирование-push): `occurred_at` фиксируется в момент факта, состав сообщения
   не меняется, порядок сохраняется. Пачка фактов, возникшая одновременно, иначе занимает основной
   поток одной задачей — [Ограничения получателей 5](limits.md#5-основной-поток-клиента).

## 3. Объявление

```js
window.dataLayer = window.dataLayer || [];
```

`window.dataLayer` не переприсваивается: массив создаётся один раз за загрузку страницы.

## 4. Структура сообщения

Сообщение имеет два уровня. Верхний — общие свойства [раздела 5](#5-общие-свойства), одинаковые
у всех событий. Вложенный `payload` — всё остальное: свойства контейнера
[раздела 6](#6-свойства-контейнера) и собственные свойства события из документа его блока.
Перечень верхнего уровня фиксирован: каждый ключ присутствует в каждом событийном сообщении и не
опускается — неполученное значение передаётся как `null`, а не пропуском ключа. `null` на месте
обязательного свойства при этом остаётся data-quality ошибкой — [Общие
правила 10](../taxonomy/taxonomy.md#10-пустые-и-неприменимые-значения). Состав `payload` устроен
иначе: свойства, событию не объявленного, в нём нет вовсе — [раздел 8](#8-значения).

```text
{ event, event_id, occurred_at, schema_version, source,
  object_class, object_type, object_name, object_version, payload }
```

```js
window.dataLayer.push({ payload: null });

window.dataLayer.push({
  event: 'game_card_activated',
  event_id: newId(),
  occurred_at: new Date().toISOString(),
  schema_version: '1:1',
  source: 'web',
  object_class: 'ui_element',
  object_type: 'game_card',
  object_name: 'purple_pills',
  object_version: 1,
  payload: {
    container_type: 'collection',
    container_name: 'popular',
    parent_container_type: 'tab_panel',
    parent_container_name: 'lobby',
    element_position: 1,
    provider: 'mascot'
  }
});
```

1. Одно событие — один событийный push, и ему предшествует сбрасывающий `{ payload: null }`.
2. Сбрасывающий push очищает модель тег-менеджера. Без него ключ, очередному событию не
   объявленный, сохранит значение прошлого сообщения.
3. Сбрасывающий push сообщением о событии не является: ключа `event` в нём нет и тегов он не
   запускает.
4. Состав верхнего уровня одинаков во всех событиях и другими ключами не дополняется.
5. `payload` собирается целиком на каждый push и от предыдущего сообщения ничего не наследует.

## 5. Общие свойства

| Свойство | Тип | Что содержит | Источник значения |
| --- | --- | --- | --- |
| `event` | string | Имя события из реестра его блока | Документ блока |
| `event_id` | string | Идентификатор отдельного события, UUID v4 | `newId()` в момент факта |
| `occurred_at` | string | Момент факта, UTC с миллисекундами | Клиент в момент факта |
| `schema_version` | string | Версия структуры события: своя у каждой пары «`event` + `object_version`» | Сборка приложения |
| `source` | string | Откуда пришло событие | Сборка приложения |
| `object_class` | string | Класс объекта: у элементов интерфейса `ui_element`, у процессов `process` | Документ блока |
| `object_type` | string | Тип объекта: тип элемента у UI, `flow` у событий самого Flow | Документ блока |
| `object_name` | string | Имя элемента в границах контейнера либо имя Flow | Каталог документа блока |
| `object_version` | integer | Версия объекта, целое не меньше `1` | Конфигурация |
| `payload` | object | Остальные свойства события | Документ блока |

1. Все десять ключей присутствуют в каждом событийном сообщении.
2. У элемента интерфейса `object_type` совпадает с объектной частью имени события посимвольно:
   у `game_card_activated` это `game_card`. У самого Flow `object_type = flow`, а объектная
   часть имени совпадает с `object_name`: у `support_chat_started` это `support_chat`. Классификация
   задаётся свойствами, а не разбором имени — [Общие правила
   4](../taxonomy/taxonomy.md#4-объекты-его-типы-и-классы).
3. У элемента интерфейса `object_name` уникален в пределах своего контейнера: одна и та же
   игра встречается в нескольких лентах. У Flow имя обозначает процесс в пределах типа `flow`,
   а конкретный запуск различает `attempt_id` в `payload` — [Правила для Flow
   5](../taxonomy/taxonomy_flow.md#5-обязательные-свойства-события-flow).
4. `object_version` версионирует объект, а не приложение, и сборкой не задаётся: значение
   приходит из конфигурации — [Общие правила 6](../taxonomy/taxonomy.md#6-версия-объекта).
5. `schema_version` задаёт сборка, но одного значения на приложение у неё нет: версия своя у
   каждой пары «`event` + `object_version`», и смена `object_version` начинает отсчёт заново —
   [Общие правила 7](../taxonomy/taxonomy.md#7-версия-схемы).
6. `schema_version` растёт при новом свойстве события и при смене типа свойства. Расширение
   перечня допустимых значений версию не меняет, а смена смысла свойства версией не решается
   вовсе: это новое имя и депрекация старого — [Общие
   правила 8](../taxonomy/taxonomy.md#8-стабильность-имён).
7. `source` называет канал, из которого пришло событие, и одинаков у всех событий одной сборки:
   от блока, страницы и места вызова он не зависит. Значения `web`, `app` и `api` перечислены
   [Общими правилами 3](../taxonomy/taxonomy.md#3-общие-свойства-для-любого-события), но закрытым
   перечнем не объявлены — [раздел 10](#10-открытые-вопросы).

Обе версии клиент получает готовыми и сам не вычисляет: `object_version` приходит из
конфигурации, `schema_version` — из сборки. Ниже — как выглядит допустимое значение каждой;
норму задают «Общие правила», таблица повторяет их [раздел 6](../taxonomy/taxonomy.md#6-версия-объекта).

| Свойство | Что версионирует | Формат | Пример |
| --- | --- | --- | --- |
| `object_version` | Устройство объекта: из чего он состоит и как себя ведёт — [Общие правила 6](../taxonomy/taxonomy.md#6-версия-объекта) | Целое число, отсчёт с `1`; значений вида `2.1`, `v2`, `2026-09-01` и номера сборки приложения не бывает | `2` |
| `schema_version` | Структуру события об этом объекте — [Общие правила 7](../taxonomy/taxonomy.md#7-версия-схемы) | Два числа через двоеточие, отсчёт с `1:1`: первое растёт при изменении состава свойств, второе — при смене их типа | `1:1` |

## 6. Свойства контейнера

Контейнер — именованная область интерфейса, в которой элемент находится. Контейнер сам является
элементом, поэтому несёт не только имя, но и тип.

| Свойство | Тип | Что содержит |
| --- | --- | --- |
| `container_type` | string | Тип контейнера: тот `object_type`, которым контейнер является как элемент |
| `container_name` | string | Имя контейнера из каталога его блока |
| `parent_container_type` | string | Тип контейнера, в который вложен `container_name` |
| `parent_container_name` | string | Имя этого родительского контейнера |
| `element_position` | integer | Позиция элемента от `1` в упорядоченном контейнере |

1. `container_type` передаётся во всех событиях элемента интерфейса: `object_name`
   идентифицирует экземпляр не сам по себе, а в границах своего контейнера.
2. `container_name` не передаётся у контейнера, единственного в своём роде: если тип контейнера
   в интерфейсе представлен ровно одним экземпляром, тип его и называет.
3. Пара `parent_container_type` и `parent_container_name` передаётся только у элементов
   вложенного контейнера и всегда вместе.
4. Родительская пара покрывает один уровень вверх. Более глубокое дерево передаётся не
   полностью — [раздел 10](#10-открытые-вопросы).
5. `element_position` передаётся только в упорядоченном контейнере. Идентификатором позиция не
   является и `object_name` не заменяет: при перестановке элементов она меняется, имя — нет.
6. Значения берутся из каталога документа блока и не строятся из маршрута, URL, DOM,
   CSS-класса, `data-*`, `aria-label` и локализованного текста.
7. Значение, отсутствующее в каталоге, — data-quality ошибка: событие не отбрасывается молча,
   но нормой такое значение не считается.

## 7. Имена событий

```text
<объект>_<действие>    nav_tab_selected, game_card_activated, support_chat_started
```

| Действие | Что означает | Пример |
| --- | --- | --- |
| `viewed` | Элемент показан пользователю | Карточка выехала в область видимости |
| `changed` | Собственное значение элемента сменилось | Строка поиска игр |
| `selected` | Элемент стал выбранным среди нескольких и остаётся выбранным | Вкладка навигации |
| `activated` | Элемент выполнил команду и состояния не удержал | Карточка запуска игры |
| `triggered` | Принята команда запустить Flow | Команда кнопки открыть чат поддержки |
| `started` | Flow инициализирован | Чат поддержки открыт и готов принять сообщение |

1. Имя пишется в нижнем регистре через `_`, объект — в единственном числе.
2. `selected` и `activated` разводит удержание состояния. Источник истины у `selected` —
   состояние, а не обработчик клика: выбор уже выбранного элемента события не даёт, а
   программная смена состояния — даёт.
3. `activated` фиксирует активацию элемента, а не результат команды: результат описывает
   событие своего объекта.
4. Повторная активация того же элемента является новым фактом: пользователь законно запускает
   игру дважды.
5. Rerender, повторная отрисовка и повторный вызов обработчика факта не создают.
6. Применение сохранённого состояния при инициализации сменой не является: иначе каждая
   загрузка страницы давала бы `selected`.
7. У UI отдельного события на каждый элемент нет: элементы различает `object_name`, а не имя
   события. У Flow имя события содержит имя процесса; его попытки различает `attempt_id`.
8. Новый `event_id` — на новый факт; повторная доставка того же факта сохраняет `event_id` и
   `occurred_at`.
9. `changed` от `selected` и `activated` отделяет собственное значение: у элемента с `changed`
   оно есть и сменилось, а выбор и команда своего значения не несут. Фильтр и строка поиска
   меняют значение, вкладка — выбирается, кнопка — выполняет команду.
10. Перечень действий пополняется по мере появления блоков. Действия UI берутся из закрытого
    перечня [Правил для элемента интерфейса 3](../taxonomy/taxonomy_ui.md#3-действия-и-состояния-элемента),
    действия Flow — из [Правил для Flow 3](../taxonomy/taxonomy_flow.md#3-состояния-и-действия-flow).
11. `triggered` фиксирует принятую команду, `started` — установленную готовность процесса.
    Клик, загрузка библиотеки и таймер сами по себе готовности не подтверждают. Состав событий,
    источники истины и дедупликацию задаёт документ конкретного Flow.

## 8. Значения

| Тип в документе | Тип в сообщении | Пример |
| --- | --- | --- |
| string | string | `'popular'` |
| integer | number, целое | `1` |
| number | number | `10.5` |

1. Свойства, событию не объявленного, в `payload` нет вовсе. Объявленное но без
   значения передаётся как `null`.
2. Строки `"null"`, `"undefined"` и пустая строка запрещены как значение любого свойства.
3. `undefined`, `NaN`, `Date`, функции и вложенные объекты внутри `payload` запрещены.
4. `event_id` — UUID v4, полученный функцией `newId()`; её реализация и порядок выбора источника
   случайности — [Клиентские приёмы 3](helpers.md#3-идентификатор-события).
5. `occurred_at` фиксируется в момент факта, а не в момент push. `Date.now()`, локальное время и
   время сервера не передаются — [Клиентские приёмы 2](helpers.md#2-время-события).

## 9. Приёмка

1. Верхний уровень содержит ровно десять ключей [раздела 5](#5-общие-свойства).
2. `payload` содержит все свойства, объявленные этому событию его документом, и только их.
3. Каждому событийному push предшествует сбрасывающий `{ payload: null }`.
4. `event` совпадает с именем из реестра своего блока посимвольно.
5. У UI `object_type` совпадает с объектной частью имени события. У самого Flow
   `object_class = process`, `object_type = flow`, объектная часть имени равна `object_name`.
6. `object_class`, `object_type` и `object_name` заполнены у каждого события.
7. `object_version` — целое число не меньше `1`.
8. `container_type` присутствует в каждом событии элемента интерфейса.
9. `parent_container_type` и `parent_container_name` присутствуют вместе либо отсутствуют вместе.
10. `element_position` присутствует только у элементов упорядоченного контейнера и начинается
    с `1`.
11. Значения `container_name`, `parent_container_name` и `object_name` найдены в каталоге
    своего блока.
12. `event_id` — валидный UUID v4, `occurred_at` — UTC с миллисекундами.
13. `null` встречается только на месте объявленного свойства с неполученным значением; строк
    `"null"`, `"undefined"` и пустых строк в сообщении нет.
14. Сообщение укладывается в бюджет [Ограничений получателей 3](limits.md#3-бюджет-события):
    не больше 25 свойств и не больше 800 байт. Событие сверх бюджета ставит под удар не себя, а
    всю группу, с которой уйдёт.
15. Значение свойства не длиннее 100 символов — [Ограничения получателей
    3](limits.md#3-бюджет-события).
16. `schema_version` — два числа через двоеточие, отсчёт с `1:1`: значения вида `1_0`, `1.0`
    и `v1` приёмку не проходят — [раздел 5](#5-общие-свойства).
17. События Flow несут в `payload` `attempt_id` формата UUID v4 и целочисленный `event_sequence`.
    Порядок событий и сохранение состояния проверяются по [Правилам передачи в dataLayer
    8](../taxonomy/datalayer.md#8-состояние-попытки) и документу Flow. Порядок отправки событий
    чата поддержки — [Поддержка 2](4.%20support.md#2-порядок-отправки).

## 10. Открытые вопросы

1. Закрытый перечень значений `source`: `web`, `app` и `api` перечислены [Общими
   правилами 3](../taxonomy/taxonomy.md#3-общие-свойства-для-любого-события), но закрытым
   перечнем не объявлены.
2. Действующие значения `schema_version`: одного значения на сайт не существует — версия своя у
   каждой пары «`event` + `object_version`», [Общие
   правила 7](../taxonomy/taxonomy.md#7-версия-схемы), а перечень значений по событиям не заведён.
3. Справочник версий объектов: где ведётся и кто присваивает следующий номер — [Общие
   правила 11](../taxonomy/taxonomy.md#11-открытые-вопросы). Вид источника закрыт: клиент читает
   значение из конфигурации — [раздел 5](#5-общие-свойства).
4. Условие показа для `viewed`: механизм и предложенные значения доли видимости и непрерывной
   длительности заданы [Клиентскими приёмами 4](helpers.md#4-отслеживание-показа), но не
   согласованы. До согласования события `viewed` в разработку не передаются.
5. Чем ограничен показ поверхности в ключах дедупликации, пока идентификатора показа нет.
6. Объём потока `viewed` относительно суточного предела выгрузки в BigQuery — [Ограничения
   получателей 4](limits.md#4-объём-потока). Поток показов исчерпывает предел раньше остальных
   событий сайта, и решение принимается до внедрения.
