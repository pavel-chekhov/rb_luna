# ТЗ блока «Поддержка»

Статус — предложение для интеграции. Документ описывает частичное отслеживание Flow `support_chat`:
команду открыть чат на сайте и готовность открытого чата принять сообщение пользователя.
Сервис чата и его сигналы пока `TBD` — [раздел 7](#7-открытые-вопросы). До их уточнения ТЗ в
разработку не передаётся; клик и таймер не заменяют подтверждение готовности.

Структура сообщения и общие свойства заданы [Общими правилами передачи в dataLayer](1.%20dataLayer.md),
свойства процесса — [Правилами для Flow](../taxonomy/taxonomy_flow.md). Получение времени и
идентификаторов описано в [Клиентских приёмах](helpers.md); состояние попытки — в
[Правилах передачи в dataLayer 8](../taxonomy/datalayer.md#8-состояние-попытки).

## 1. Идентификация Flow

Блок — визитка с заголовком «Поддержка», текстом «Свяжитесь с нами, если у вас остались вопросы»
и кнопкой «В поддержку». Кнопка открывает чат на сайте. Визитка служит точкой входа в процесс.

| Параметр | Значение |
| --- | --- |
| `object_class` | `process` |
| `object_type` | `flow` |
| `object_name` | `support_chat` |
| `source` | `web` |
| Аналитическая задача | Измерить, сколько принятых команд открыть чат заканчиваются готовностью чата к общению |
| Точка входа | Кнопка «В поддержку» в визитке, `trigger_source = support_card` |
| Открывает попытку | `support_chat_triggered` |
| Устанавливает начало Flow | `support_chat_started` |
| Текущее покрытие | Только `triggered` и `started`; результат обращения не отслеживается |

Это согласованное исключение для частичного отслеживания поддержки — [Правила для Flow
2](../taxonomy/taxonomy_flow.md#2-что-является-flow). Полный тест `started` + `completed` текущим
реестром не покрыт. Готовность чата не означает, что сообщение отправлено или вопрос пользователя
решён. Цель полного Flow и источник подтверждения результата — `TBD`, вне текущего внедрения.

Конверсия запуска — доля уникальных `attempt_id` с `support_chat_started` среди попыток с
`support_chat_triggered`. Пару связывают по `attempt_id`, а время готовности считают как разницу
`occurred_at` этих событий. Попытка без `started` означает только отсутствие зарегистрированной
готовности: это не подтверждение ошибки, отмены или успешного завершения. Попытки, ещё ожидающие
готовности, могут получить `started` позже.

### 1.1. Попытка запуска

Одна попытка соответствует одному запуску чата из данной визитки. Её границы — узкое исключение
из [Правил для Flow 4](../taxonomy/taxonomy_flow.md#4-попытка): локальный цикл отслеживания может
закончиться без завершающего аналитического события.

1. При принятии команды открыть чат клиент создаёт `attempt_id` функцией `newId()`, фиксирует
   версию процесса и отправляет `support_chat_triggered` с `event_sequence = 1`. Состояние попытки
   создаётся до вызова открытия чата, чтобы синхронный callback готовности не опередил команду.
2. Подтверждение, что чат открыт и готов принять сообщение, даёт один `support_chat_started` с тем же
   `attempt_id` и `event_sequence = 2`. Самого вызова метода открытия, загрузки библиотеки,
   монтирования компонента или появления индикатора загрузки недостаточно.
3. Пока чат открывается или уже открыт, повторные нажатия не создают новый запуск и новых
   событий не дают. Повторные уведомления готовности и rerender не повторяют `started`.
4. Подтверждённое закрытие чата завершает локальный цикл, в том числе если чат закрыли до
   готовности. Следующая принятая команда запуска создаёт новый `attempt_id` и начинает
   последовательность с `1`. Само закрытие событий не даёт.
5. Подтверждённая ошибка открытия завершает локальный цикл без `started`. Следующая принятая
   команда повторить запуск создаёт новую попытку. Отсутствие callback, истечение произвольного
   таймера и перезагрузка подтверждённой ошибкой не являются.
6. Перезагрузка сама по себе не создаёт новую попытку и не закрывает прежнюю. Хранилище сохраняет
   `attempt_id`, `object_version`, счётчик, состояние запуска и признаки уже отправленных событий.
   Если готовность ещё не была учтена, её подтверждение после восстановления даёт `started` с
   номером `2`; если была — повторное уведомление событий не даёт. Механизм восстановления и
   поведение при нескольких вкладках — `TBD`.
7. Callback должен относиться к действующему запуску. Уведомление от предыдущего закрытого или
   неудачного запуска игнорируется и к новой попытке не присоединяется. Способ связать callback
   с запуском — `TBD`; все поздние уведомления, включая закрытие и ошибку, проходят эту проверку.
8. Повторная доставка уже созданного события сохраняет `event_id`, `occurred_at`, `attempt_id`
   и `event_sequence`; счётчик повторная доставка не расходует. Сбрасывающий push также его не
   расходует.
9. Закрытие и ошибка завершают только локальный цикл отслеживания запуска. События `completed`,
   `cancelled`, `failed` и другие события Flow сейчас не отправляются; результат обращения из
   локального состояния не выводится.

## 2. Версия процесса

`object_version` клиент получает из конфигурации при создании попытки и сохраняет неизменным до
конца её локального цикла — [Правила передачи в dataLayer
8](../taxonomy/datalayer.md#8-состояние-попытки). Версию меняют по [Правилам для Flow
6](../taxonomy/taxonomy_flow.md#6-версия-процесса), а не при смене текста визитки или сборки.

`schema_version` задаёт сборка отдельно для каждой пары «`event` + `object_version`» — [Общие
правила 5](1.%20dataLayer.md#5-общие-свойства). В примерах первая версия процесса равна `1`,
версии схем обоих событий — `'1:1'`; реальные значения приходят из конфигурации и сборки.

## 3. Реестр событий

Ровно два события. Оба обязательны при наступлении своего факта и несут свойства
[раздела 6](#6-свойства).

| Событие | Когда отправляется | Источник истины | Ключ дедупликации |
| --- | --- | --- | --- |
| `support_chat_triggered` | Клиент принял команду кнопки «В поддержку» открыть чат, до его инициализации | Обработчик принятой команды запуска на клиенте | `attempt_id + event` |
| `support_chat_started` | Чат открыт и готов принять сообщение пользователя | Подтверждённое состояние чата; сервис и конкретный сигнал — `TBD` | `attempt_id + event` |

1. Активация кнопки мышью, касанием и клавиатурой имеет одну семантику пользовательской команды.
   Отдельного события `button_activated` это ТЗ не вводит.
2. Показ визитки и кнопки событий не создаёт. Само появление оболочки чата без готовности
   принять сообщение не создаёт `support_chat_started`.
3. Запуски через другие точки входа, автоматическое открытие, отправка сообщений и результат
   обращения в текущий реестр не входят. Другим точкам входа значение `support_card` не присваивается.
4. Даже при мгновенном открытии порядок — `triggered`, затем `started`; `occurred_at` фиксируется
   отдельно в момент каждого факта. События не копятся в ожидании второго события пары.

## 4. Каталог шагов

В текущем внедрении шаги не объявлены. Событий `support_chat_step_*` и свойств `step_name`,
`step_number` нет. Готовность чата учитывается событием самого Flow — `support_chat_started`.

## 5. Каталог входных значений

В текущем внедрении входные значения не объявлены. Событий `support_chat_input_*` и свойства
`input_name` нет. Текст сообщения, контактные данные, идентификатор обращения и результат
переписки свойствами этих двух событий не являются.

## 6. Свойства

Общие десять ключей верхнего уровня заданы [Общими правилами 5](1.%20dataLayer.md#5-общие-свойства).
Значения классификации этого Flow перечислены в [разделе 1](#1-идентификация-flow). Ниже — полный
состав `payload`; свойства контейнера и собственные бизнес-свойства этим событиям не объявлены.

| Свойство | Тип | Где обязательно | Значение | Источник |
| --- | --- | --- | --- | --- |
| `attempt_id` | string | Оба события | UUID v4, один на запуск | `newId()` при принятии команды; далее состояние попытки |
| `event_sequence` | integer | Оба события | `1` у `triggered`, `2` у `started` | Счётчик очереди отправки попытки |
| `trigger_type` | string | Только `support_chat_triggered` | `user_action` | Принятая пользовательская команда |
| `trigger_source` | string | Только `support_chat_triggered` | `support_card` | Каталог точки входа этого документа |

`user_action` и `support_card` — предлагаемые значения для этой интеграции, а не общий
справочник всех способов и источников запуска на сайте. Они не вычисляются из текста кнопки,
DOM, CSS-классов или URL. У `support_chat_started` ключей `trigger_type` и `trigger_source` нет вовсе:
источник запуска восстанавливается по `attempt_id` из `support_chat_triggered`.

Формат `attempt_id` и генератор заданы [Правилами передачи в dataLayer
6](../taxonomy/datalayer.md#6-идентификаторы); правила счётчика — [Правилами для Flow
9](../taxonomy/taxonomy_flow.md#9-порядковый-номер-события).

### 6.1. Примеры сообщений

Принята команда кнопки «В поддержку» открыть чат:

```js
window.dataLayer.push({ payload: null });

window.dataLayer.push({
  event: 'support_chat_triggered',
  event_id: 'c4eb8d71-2fa6-4e90-9b35-7d0612c8fa43',
  occurred_at: '2026-09-09T16:23:53.120Z',
  schema_version: '1:1',
  source: 'web',
  object_class: 'process',
  object_type: 'flow',
  object_name: 'support_chat',
  object_version: 1,
  payload: {
    attempt_id: 'f2a67419-8bd3-4ce0-a175-6d092eb834fc',
    event_sequence: 1,
    trigger_type: 'user_action',
    trigger_source: 'support_card'
  }
});
```

Чат этого же запуска открыт и готов принять сообщение:

```js
window.dataLayer.push({ payload: null });

window.dataLayer.push({
  event: 'support_chat_started',
  event_id: 'ab6310d2-e9f4-47a8-b650-3c71d29e084f',
  occurred_at: '2026-09-09T16:23:53.840Z',
  schema_version: '1:1',
  source: 'web',
  object_class: 'process',
  object_type: 'flow',
  object_name: 'support_chat',
  object_version: 1,
  payload: {
    attempt_id: 'f2a67419-8bd3-4ce0-a175-6d092eb834fc',
    event_sequence: 2
  }
});
```

Примеры показывают сообщения двух отдельных фактов, а не код, который нужно выполнить подряд
при клике. Идентификаторы и время здесь иллюстративные; в реализации они получаются в момент факта.

### 6.2. Приёмка

В дополнение к [Общим правилам 9](1.%20dataLayer.md#9-приёмка):

| Сценарий | Ожидаемый результат |
| --- | --- |
| Визитка показана; библиотека загружена; появился индикатор загрузки | Сами эти факты событий не дают |
| Команда принята, затем подтверждена готовность | Одна пара `triggered` → `started`, общий `attempt_id`, номера `1` → `2`, разные `event_id` |
| Готовность подтверждена синхронно при вызове открытия | `triggered` всё равно передан раньше `started` |
| Кнопка активирована клавиатурой | Та же пара событий, `trigger_type = user_action` |
| Двойное нажатие во время открытия или нажатие при открытом чате | Новых попыток и дополнительных событий нет |
| Повторный callback готовности или rerender | Дополнительного `started` нет |
| Подтверждена ошибка открытия | Только `triggered`; при новой принятой команде — новый `attempt_id` и номер `1` |
| Подтверждено закрытие до готовности | Только `triggered`; поздний callback готовности игнорируется |
| Чат закрыт после готовности и открыт заново | Закрытие событий не даёт; новый запуск создаёт новую пару с новым `attempt_id` |
| Перезагрузка между командой и готовностью | Прежние `attempt_id` и версия сохранены; при подтверждении готовности один `started` с номером `2` |
| Перезагрузка после отправленного `started` | Восстановление не повторяет пару и не создаёт новую попытку |
| Поздний callback предыдущего запуска при новой попытке | Не создаёт события и не меняет состояние новой попытки |
| Нет подтверждения готовности, закрытия или ошибки | По таймеру события не создаются и попытка не сбрасывается |
| Повторная доставка того же факта | Сохранены `event_id`, `occurred_at`, `attempt_id`, `event_sequence` |

Проверить также ровно десять верхнеуровневых ключей, точный состав `payload` по
[разделу 6](#6-свойства), валидные UUID v4, UTC с миллисекундами, сбрасывающий push перед каждым
событием и бюджет сообщения. Ключи `trigger_type` и `trigger_source` не должны наследоваться
в `started`. Кроме двух имён из реестра блок событий не отправляет.
